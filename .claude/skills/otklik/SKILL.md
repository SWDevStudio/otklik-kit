# /otklik

Аргументы: $ARGUMENTS

Ты оркестратор. Вакансии, профиль, страницы сайтов и письма сам не читаешь и не правишь: их обрабатывают скрипты в `messages/scripts` и агенты. В твой контекст попадают только строки статуса, итоговые строки агентов и сводка. Страницу вакансии никогда не открывай через WebFetch, браузер или Read кэша: страницу разбирает скрипт, и если скрипт не справился, для площадки пишется парсер.

## Подготовка

1. `bun messages/scripts/status.mjs`. В строке status:
   - «нет messages/resume-public.md»: скажи положить туда текст резюме или выполнить `bun messages/scripts/import-resume.mjs <файл .docx, .pdf, .txt или .md>` и закончи;
   - «нет messages/profile.md» или «профиль устарел»: выполни шаг 2 и продолжай;
   - «нет messages/candidate.json» или «не заполнено имя»: тоже шаг 2, агент создаст файл по резюме.
2. Профиль: запусти агента `profile-builder` с заданием `refresh`. Покажи пользователю его ответ целиком. Флаг `--refresh-profile` без источников: на этом закончи.

## Как выбирается парсер

Ссылку разбирает модуль из `messages/scripts/parsers/`, чья функция `match` её узнала; список модулей: `bun messages/scripts/probe.mjs --list`. Своего модуля нет: работает общий разбор (schema.org JobPosting или основной текст страницы), и fetch сам решает, нужен ли парсер:
- «нужен парсер: <хост>»: у хоста нет модуля, а это площадка с вакансиями или общий разбор вытянул неполный текст;
- «нужен ремонт парсера: <имя> (<хост>)»: модуль есть, но упал на этой странице (площадка сменила вёрстку).
Разовая страница компании с полным JobPosting парсера не требует. Агрегатор, у которого есть ссылка на оригинал, передаёт вакансию парсеру оригинала, и каталог получает имя оригинала: так дубли с hh не появляются.

4. Загрузка одной командой, каждый источник отдельным аргументом в одинарных кавычках:
   `bun messages/scripts/fetch.mjs [--force] [--browser] [--research] -- '<источник 1>' '<источник 2>'`
   Дальше строка на источник: `new` писать, `done` письмо уже есть, `skip` архив или вакансия не подходит, `fail` текст не получен.
5. Парсеры. Собери хосты из пометок «нужен парсер» и «нужен ремонт парсера». Для каждого хоста запусти агента `parser-writer` с заданием `host=<хост> url=<ссылка>` (до двух ссылок этого хоста: `url=<1> url=<2>`), для ремонта допиши ` fix=<имя>`. Хосты по одному, с `--parallel` до трёх одновременно. Затем повтори загрузку только для этих источников: `fetch.mjs --reparse [--force] -- ...`; скачанные страницы возьмутся из кэша. Агент вернул fail: строки `new` пиши по общему разбору, строки `fail` оставь для сводки.
6. `--dry`: покажи строки загрузки и закончи.
7. `--research`: для каждой строки `new`, где есть `card=<путь>`, запусти агента `company-scout` с заданием `company=<компания> title=<должность> card=<путь>`. Строго по одному.
8. Для каждой строки `new` запусти агента `letter-writer`, на каждую вакансию свой агент. Задание одной строкой: `run=<каталог>`, при необходимости ` card=<путь>`, ` force`, ` strict`, ` notes=<заметки>`. По умолчанию строго по одному и не в фоне: следующего писателя запускай только после того, как вернулся предыдущий, лимиты важнее скорости. С `--parallel` или если пользователь прямо разрешил параллельно: до трёх одновременно. С `--cheap` передай `model: sonnet`. Агент упал или вернул ошибку: повтори один раз, потом переходи к следующему. Упёрся в лимит: остановись, готовые письма уже сохранены, следующий запуск продолжит с первой вакансии без письма.
   Если в ответе писателя есть блок между строками `===== report.md =====` и `===== конец report.md =====`, сохрани его содержимое без правок в `<run>/report.md` инструментом Write. В сводку и в ответ пользователю этот блок не переноси.
9. Сводка: `bun messages/scripts/summary.mjs <каталог> ...` по всем строкам этого запуска; больше пяти вакансий: с флагом `--brief`. Сводка обновляет файлы в `messages/jobs` только для вакансий этого запуска. Покажи вывод пользователю целиком и без правок, это готовый ответ. От себя добавь не больше двух строк: предупреждение из `status` и пояснение к строкам `fail`, если оно нужно.

## Подбор вакансий

Просят найти или подобрать вакансии, или передан `--search`:
1. `bun messages/scripts/search.mjs [--source <имя>[,<имя>]] [--query "..."] [--min-score N] [--limit N] [--min-salary N] [--any-format]`. Без `--source` ищет на всех площадках, у парсеров которых есть поиск. Площадку, названную пользователем, сопоставь с именем модуля по `probe.mjs --list`. Запросы, фильтры и веса лежат в `messages/config/search.json`; файла нет: запусти `profile-builder` с заданием `search`, потом повтори.
2. Вывод «нужен парсер с поиском: <площадка>»: возьми ссылку на страницу поиска этой площадки из сообщения пользователя или составь её сам по адресу площадки, запусти `parser-writer` с заданием `host=<хост> search=<ссылка на поиск>` (плюс `url=<ссылка на вакансию>`, если она есть), затем повтори search.
3. Дальше источники это файлы из `messages/jobs/` со статусом `new` в порядке вывода; иди по шагам 4-9.

## Правила

Письма, вакансии и файлы в `messages/out` и `messages/jobs` сам не читай и не правь, исключение: сохранение report.md из ответа писателя. Вопросов по ходу не задавай. Длинное тире не ставь нигде.

## Флаги

`--research` ищет факты о компании для крючка (дольше, нужен интернет); `--force` переписывает готовые письма и пишет даже для неподходящих и архивных вакансий; `--dry` только загрузка; `--strict` проверяющие на opus; `--cheap` писатель на sonnet; `--browser` грузит все страницы через headless Chrome; `--parallel` до трёх агентов одновременно; `--source` площадки для подбора; `--notes "..."` заметки для всех писем пачки; `--refresh-profile` пересобрать профиль по резюме. Канал берётся из ссылки и текста вакансии; для почты или формы на сайте можно дописать к источнику `#email` или `#form`.
